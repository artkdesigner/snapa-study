# Ship safely: безопасность, ревью, эксплуатация

Шесть правил, которые применяются к каждому проекту поверх вёрстки
(`figma-to-code`). Большинство из них — не разовая настройка, а то, за чем
агент следит постоянно: увидел нарушение — сказал об этом сразу, не дожидаясь
вопроса.

Что относится к проекту, зависит от его устройства:

| Правило                               | Статичный сайт на GitHub Pages | Есть бэкенд/БД/ЛК | Свой VPS        |
| ------------------------------------- | ------------------------------ | ----------------- | --------------- |
| 1. Секреты + Gitleaks                 | да                             | да                | да              |
| 2. SSH по ключам + Fail2ban           | —                              | —                 | да              |
| 3. RLS                                | —                              | да                | да, если там БД |
| 4. Ревью вторым агентом               | да                             | да                | да              |
| 5. `/code-review ultra` перед релизом | желательно                     | да                | да              |
| 6. Автомониторинг                     | —                              | —                 | да              |

## 1. Секреты: ни в промпт, ни в git

**В промпт — никогда.** API-ключи платёжек, баз данных, сервисов не пишутся
текстом в чат с агентом: переписка логируется и может уйти в чужие руки.
Правильно — пользователь сам кладёт ключ в `.env`, агент ссылается на имя
переменной (`STRIPE_SECRET_KEY`), а не на значение. Если пользователь всё-таки
вставил ключ в чат — не использовать его молча, а сказать: «ключ засвечен,
перевыпусти его в кабинете сервиса и положи новый в `.env`».

**`.env` закрыт от репозитория.** В `.gitignore` каждого проекта:

```
.env
.env.*
!.env.example
```

В репозиторий идёт только `.env.example` — имена переменных с пустыми
значениями, как документация. Перед первым коммитом проверить:
`git check-ignore .env` должен вывести `.env`.

**Ловушка Vite: `VITE_`-переменные уезжают в браузер.** Всё, что начинается с
`VITE_`, Vite вшивает в JS-бандл открытым текстом — любой посетитель увидит
это в DevTools. Туда можно только публичные ключи, которые и задуманы для
клиента (Supabase `anon`, Stripe `publishable`, Яндекс.Карты JS API).
Секретные ключи (Stripe `secret`, Supabase `service_role`, ключи ЮKassa/
CloudPayments, пароли БД, токены ботов) — только на сервере или в
serverless/edge-функции, без префикса `VITE_`. Увидел секретный ключ под
`VITE_` — это утечка, даже если `.env` в `.gitignore`.

**Gitleaks — автоматический сканер утечек.** Ставится в каждый проект на двух
уровнях:

1. Локально, pre-commit хук — ловит ключ до того, как он попал в историю.
   Без Python/`pre-commit`, обычным git-хуком:

   ```sh
   mkdir -p .githooks
   cat > .githooks/pre-commit <<'EOF'
   #!/bin/sh
   command -v gitleaks >/dev/null || { echo "gitleaks не установлен — пропускаю скан"; exit 0; }
   exec gitleaks git --pre-commit --redact --staged --verbose
   EOF
   chmod +x .githooks/pre-commit
   git config core.hooksPath .githooks
   ```

   Установка бинарника: `brew install gitleaks` (macOS) или релиз с
   github.com/gitleaks/gitleaks/releases (Linux). `core.hooksPath` — локальная
   настройка git, её нужно выполнить заново после каждого `git clone`.

2. В CI — страховка на случай, если хук не стоит или его обошли.
   `.github/workflows/gitleaks.yml`:

   ```yaml
   name: gitleaks
   on: [push, pull_request]
   jobs:
     scan:
       runs-on: ubuntu-latest
       steps:
         - uses: actions/checkout@v4
           with: { fetch-depth: 0 }
         - uses: gitleaks/gitleaks-action@v2
           env:
             GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
   ```

Для уже существующего репо перед первым пушем — прогнать всю историю:
`gitleaks git -v`.

**Если ключ уже утёк в git** — удаление файла или коммита не помогает: он
остаётся в истории, форках и кешах GitHub. Первым делом **перевыпустить
(отозвать) ключ** в кабинете сервиса, только потом чистить историю.

**Дополнительно — Codex Security** (OpenAI): агент, который строит модель
угроз проекта и ищет уязвимости глубже шаблонного сканера — например, логические
дыры в проверке прав. Research preview с марта 2026, доступен на платных планах
ChatGPT (Pro/Business/Enterprise/Edu); CLI и SDK открыты под Apache 2.0 с июля 2026. Запускает пользователь сам — агент только предлагает его перед релизом
проектов с бэкендом/оплатой, для статичного лендинга избыточно.

## 2. Сервер: вход только по SSH-ключам + Fail2ban

Пароли на открытый SSH-порт боты перебирают непрерывно, а ключ подобрать
нельзя. Поэтому на любом боевом VPS вход только по ключам.

Порядок важен — иначе можно закрыть себе доступ к серверу:

1. Ключ уже лежит в `~/.ssh/authorized_keys` на сервере (`ssh-copy-id`).
2. **Во второй, отдельной сессии** проверить, что вход по ключу работает.
   Первую сессию не закрывать до конца настройки.
3. В `/etc/ssh/sshd_config` (или файле в `/etc/ssh/sshd_config.d/`):

   ```
   PasswordAuthentication no
   KbdInteractiveAuthentication no
   PermitRootLogin prohibit-password
   ```

4. `sshd -t` (проверка синтаксиса) → `systemctl reload ssh` → снова войти
   из новой сессии, убедиться, что пускает.

Правка `sshd_config` на чужом/боевом сервере — только с явного подтверждения
пользователя: ошибка = потерянный доступ.

**Fail2ban** — блокирует IP после серии неудачных попыток входа:

```sh
apt install fail2ban
cat > /etc/fail2ban/jail.local <<'EOF'
[sshd]
enabled  = true
port     = 2222        # реальный SSH-порт сервера, если он не 22
maxretry = 5
findtime = 10m
bantime  = 1h
EOF
systemctl enable --now fail2ban
fail2ban-client status sshd
```

## 3. RLS: правила доступа к строкам в базе

Личный кабинет и любая БД, к которой ходит фронтенд, работают только с
включённым **Row Level Security** — правилами, которые определяют, какие строки
видит конкретный пользователь. Без RLS пользователь может обычным запросом
(из DevTools, с тем же публичным `anon`-ключом) прочитать или изменить чужие
данные — сайт при этом выглядит рабочим.

Правила (Supabase / Postgres):

- RLS включён на **каждой** таблице схемы, доступной API (в Supabase — `public`):
  `alter table <t> enable row level security;`. Включённый RLS без политик =
  «доступ закрыт всем», и это правильная точка старта.
- Политики — явно на каждую операцию (`select`/`insert`/`update`/`delete`),
  привязка к пользователю через `auth.uid()`:

  ```sql
  create policy "own rows: read" on orders
    for select using (user_id = auth.uid());
  create policy "own rows: insert" on orders
    for insert with check (user_id = auth.uid());
  ```

  `update` требует и `using`, и `with check` — иначе можно переписать
  `user_id` на чужой.

- Ключ `service_role` обходит RLS — только на сервере, никогда во фронтенде
  (см. правило 1 про `VITE_`).
- Проверка перед релизом — таблицы без RLS:

  ```sql
  select schemaname, tablename from pg_tables
  where schemaname = 'public' and not rowsecurity;
  ```

  Пустой результат = ок. Плюс ручной тест: войти вторым тестовым пользователем
  и попробовать запросить данные первого — должно вернуться пусто.

Скрыть кнопку в интерфейсе — не защита. Проверка прав всегда на стороне базы
или сервера.

## 4. Код-ревью вторым агентом

Автор кода плохо видит свои ошибки — и агент тоже. После каждого законченного
куска работы (фича, секция, интеграция) ревью делает **независимый критик**:
отдельный запуск со свежим контекстом, а не «перечитай, что ты написал».

- **`/code-review`** — встроенная проверка Claude Code. Ищет скрытые баги в
  свежих правках (текущий diff, ветка или PR). Уровни: `low`/`medium` — только
  уверенные находки; `high`/`max` — шире охват, возможны спорные. `--fix`
  применяет исправления. Запускать после каждого значимого блока правок.
- **`code-review` Мэтта Покока** (github.com/mattpocock/skills) — проверяет
  другое: не «есть ли баг», а **соответствует ли код вашему ТЗ и стандартам
  проекта**. Работает как придирчивый техдир: два параллельных субагента —
  _Standards_ (правила из документации репо + базовый набор code smells по
  Фаулеру) и _Spec_ (что из ТЗ не сделано, что сделано лишнего, что сделано
  неправильно). Отчёты по двум осям не смешиваются.

  Установка: `/plugin install mattpocock-skills`, затем один раз
  `/setup-matt-pocock-skills`. Внутри плагина скилл называется так же, как
  встроенный, поэтому вызывать его с префиксом: `/mattpocock-skills:code-review`.
  Скиллу нужны:
  - **точка отсчёта** — коммит/ветка, от которой смотреть diff (`main`,
    `HEAD~5`, тег);
  - **ТЗ** — файл в `docs/` или `specs/` (например `docs/spec.md`) или ссылка
    на issue в коммите. Нет ТЗ — ось _Spec_ пропускается, поэтому ТЗ
    проекта стоит сохранять файлом в репо с самого начала;
  - **стандарты** — у нас это `CLAUDE.md` проекта и скилл `figma-to-code`
    (имена слоёв как классы, ноль сырых px, токены из `@theme`). Указать их
    явно, если скилл их не нашёл сам.

Порядок: сначала `/code-review` (баги), потом ревью Покока (ТЗ + стандарты).
Находки исправлять, а не просто пересказывать пользователю.

## 5. Перед финальным релизом — `/code-review ultra`

Глубокий прогон: поднимает изолированную облачную среду, несколько агентов
ищут ошибки и **воспроизводят** их, чтобы отсеять галлюцинации — в отчёт
попадают только подтверждённые проблемы.

- Запускает **только пользователь**, он платный. Агент не может и не должен
  пытаться запустить его сам — перед релизом он напоминает: «перед
  выкаткой запусти `/code-review ultra`».
- Без аргумента проверяет текущую локальную ветку (GitHub-remote не нужен,
  нужен git-репозиторий); `/code-review ultra <номер PR>` — конкретный PR.
- Это финальная проверка перед релизом, а не на каждый коммит — на каждый
  коммит достаточно правила 4.

## 6. Автомониторинг сайта на VPS

Только если проект крутится на своём сервере (для GitHub Pages это не нужно:
за доступность отвечает GitHub).

**Beszel** — лёгкий мониторинг: hub (веб-панель) + agent на каждом сервере.
Следит за CPU, памятью, диском, сетью, Docker-контейнерами и доступностью
системы. Алерты настраиваются в панели по порогам (нагрузка, память, диск,
«система недоступна») и шлются в Telegram через URL уведомления:

```
telegram://<BOT_TOKEN>@telegram?chats=<CHAT_ID>
```

Токен бота — секрет (правило 1): вводится в панели Beszel, в репо не кладётся.

**Агент на логах** поверх Beszel — чтобы алерт был не «memory > 90%», а
понятным объяснением, и чтобы типовые сбои чинились сами:

1. Триггер — Beszel generic-webhook (`generic://...?template=json`) или
   systemd-таймер раз в N минут, проверяющий `systemctl is-failed`, код ответа
   сайта (`curl -fsS`), `free -m`, `df -h`.
2. При срабатывании скрипт собирает контекст: `journalctl -u <сервис> -n 200`,
   `docker logs --tail 200 <контейнер>`, `dmesg | grep -i oom`, текущие метрики.
3. Отдаёт это `claude -p` с узким набором разрешённых инструментов и просит
   объяснить причину человеческим языком (что упало, почему, что сделано,
   что нужно от владельца).
4. **Автоисправление — только из белого списка типовых сбоев**: сервис упал
   или убит по OOM → `systemctl restart <сервис>` / `docker restart
<контейнер>`; забит диск логами → `journalctl --vacuum-size=500M`.
   Не больше одной-двух попыток подряд; если после рестарта снова падает —
   не зацикливаться, а эскалировать человеку.
5. Всё остальное (правка конфигов, удаление данных, миграции, обновление
   пакетов) — агент только описывает в Telegram и ждёт человека.
6. Результат — сообщение в Telegram: что случилось → причина → что сделано
   автоматически → нужно ли вмешательство.
